# The studio (web app)

A drum-chart studio with two ways in:

- **Create a Beat**: describe a groove in your own words. You get an original, playable,
  editable chart, generated and checked on the server. It needs no recordings and no AI
  service.
- **Song to Chart**: find a recording. Open its stored chart, or transcribe audio you
  have the right to use.

Either way you end in the same **chart workspace**:

- engraved notation;
- a beat grid on the same data;
- playback;
- undo and redo;
- versions;
- PDF, MusicXML and MIDI export, and printing.

```bash
pip install -e '.[web]'                       # FastAPI, uvicorn, httpx, the Anthropic SDK
python -m drum_agent doctor                   # LilyPond, ffmpeg, the classifier weights
python -m drum_agent serve --seed-examples    # http://127.0.0.1:8000
```

`--seed-examples` stores the Northbound example song (an original composition) as an
existing chart, so the catalog isn't empty. A song list (for instance the 100-song
workbook exported as CSV with `title` and `artist` columns) is added with
`python -m drum_agent catalog import songs.csv`. Each song is stored as
`NEEDS_SOURCE`: no chart is generated and nothing is analysed until an authorized
recording is supplied.

Configuration is in `.env.example`. Every key stays on the server.

## Create a Beat

1. **Describe it.** "Create a powerful pop-punk beat at 165 BPM in 4/4 with
   eighth-note hi-hats, a driving kick and a two-bar tom fill every eight bars."
   - While you type, the page shows what was understood (style, tempo, meter, length,
     parts, fills, ending) and which values are defaults.
   - Quick settings override the description.
   - The example chips fill in a description.
2. **Generate.** A job runs these stages: read the description, write the groove,
   fills and ending, validate every bar, engrave, draw the on-screen chart, save. The
   page shows the stages as the server reports them.
3. **The workspace opens** on version 1 of a new project in My Charts.

The generator is in `drum_agent/generate/`:

- **`parse.py`** reads the description by rules. With Claude configured, Claude reads it
  too and fills in the musical judgement the rules left at defaults. Numbers the rules
  read exactly (tempo, meter, length) and the quick settings always win.
- **`spec.py`** holds the `BeatSpec`. It validates and clamps anything from outside.
- **`styles.py`** holds 20 styles as drumming conventions, not fixed patterns: where the
  backbeat falls, what the kick leans on, the cymbal hand, idiomatic syncopations, fill
  phrasing, and what a chorus or breakdown changes.
- **`engine.py`** writes the strokes:
  - it plans the sections (intro, verse, chorus, bridge, outro, from the length or as
    asked);
  - it writes each section's groove on a metric grid;
  - it varies the last bar of each phrase;
  - it places fills where asked (a two-bar fill becomes a build plus a tom fill),
    crashes after fills and at section starts, and the ending;
  - it removes anything one drummer can't play (never three hands at once).
- **Seeds.** Randomness is seeded per layer (kick, snare and ghosts, hats, fills,
  variation), and each optional stroke has a fixed draw compared with its probability.
  So:
  - the same spec gives the same beat;
  - "new kick part" changes only the kick;
  - "more complex" adds strokes to the same groove instead of writing another one.
- **`edits.py`** applies changes to a working score:
  - **Settings changes** regenerate with the same seeds: simpler, more complex, length,
    feel, style.
  - **Part swaps** replace only that part and keep your other hand edits: hi-hat or
    ride, kick, ghost notes, or a rewrite of the selected bars.
  - **Direct edits** write into the score: add a fill, an ending, a crash, a tempo,
    copy or clear bars.
  - **Plain-language commands** use the same operations: "Replace the final bar with a
    tom fill", "Add an eighth-note kick variation to the last two bars", "Make the
    hi-hat busier but keep the kick and snare".

  A command the rules can't read is rewritten by Claude (when configured) into the
  editor's own commands, which are then applied and checked. Otherwise it is reported
  as unsupported, with examples. It is never silently ignored.
- **Generated beats only.** Operations that regenerate parts are refused for
  transcriptions and written charts: for those, edit the notes in the grid.

An original beat is checked for structure and playability: bar lengths, grid,
duplicates, kit, tempo, sections, limbs. It is never compared with a recording, and it
prints as "Original Beat, generated by Drum Agent".

## The chart workspace

- **Notation** is LilyPond's engraving, the same as the PDF. Edits are re-engraved for
  the screen as you go (`POST /api/preview`: SVG pages, no PDF, cached by content). The
  bar map marks the bars, the playing bar and the exact note being played, and lets you
  select and jump.
- **The beat grid** edits the same working score:
  - one lane per instrument, with mute and solo;
  - a step resolution that always shows every stroke (16ths, triplets, 32nds);
  - tools for hit, accent, ghost, flam and erase;
  - keyboard navigation (arrow keys, Enter or Space);
  - copy a bar to the next one, or clear a bar.

  Editing the grid changes the score, and the notation is re-engraved from it: the two
  can't disagree.
- **Playback** uses Web Audio, scheduled on the audio clock (a look-ahead scheduler), so
  timing doesn't drift.
  - **Sounds:** the acoustic kit is sampled drums rendered once on the server from the
    FluidR3 GM soundfont (MIT licence), with the kit's own MIDI notes; no audio is
    committed or downloaded. The electronic kit is synthesized in the browser, and covers
    any instrument without a sample.
  - **Controls:** play, pause and stop; loop the chart or play only the selection;
    count-in; metronome; tempo (a chart edit); practice speed (playback only); volume;
    mute and solo per instrument; follow.
  - **Highlighting:** the current bar and note are highlighted in the notation and the
    grid.
  - **Transcriptions** play their drum part, and can be heard against the recording they
    were transcribed from ("What you hear": chart drums, recording + chart, recording
    only). The chart knows where each bar starts in the recording (the performed bar
    starts), so the bars, strokes, click, cursor and loop are moved onto the recording's
    own time and the recording plays on the same audio clock: what you hear and the bar
    you see are the same, tempo drift included. The recording is the project's own
    upload, served only to its owner (`GET /api/charts/{id}/audio`). Practice speed
    changes its pitch too. When an edit adds or removes bars, the recording can no
    longer follow that version and the page says so.
- **Editing history:** undo and redo (Ctrl+Z, Ctrl+Shift+Z) work on the score itself.
- **Drafts.** Every unsaved change is kept as a draft, on the server
  (`PUT /api/projects/{id}/draft`) and in this browser. Reloading restores it, with a
  way to discard it. Leaving with an unsaved draft asks first.
- **Versions.** *Save version* writes the next immutable version: full export, every
  format cross-checked, validation, on-screen pages. Earlier versions can be opened or
  restored as the newest. Export and print save first if there are unsaved changes, so
  a file always matches a version.
- **Side panels:**
  - **Shape the beat** (beats): new beat, variation, simpler, more complex, add fill,
    new hi-hat, kick or ghost-note part, rewrite the selection, ending, feel, length,
    style.
  - **Review flagged bars** (transcriptions).
  - **Edit with words.**
  - **Sections:** rename them, and Claude suggestions for transcriptions.
  - **Checks.**
  - **Versions.**
  - **Details:** the description and what was understood, or the recording and the
    engine.

## My Charts and Settings

- **My Charts** lists every project, original beats and song charts, newest first. You
  can search, filter, open, rename, duplicate and delete (with a confirmation that says
  what goes). Each card shows the kind, the status, versions, tempo and the last
  update. Nothing is invented to fill the page: an empty library says so.
- **Settings** cover:
  - in this browser: theme (dark, light, system), motion (system, reduce, full), drum
    sounds, count-in, metronome, follow;
  - from `/api/health`, what the server has: LilyPond, ffmpeg, the model, Claude, the
    search providers, the licensed-audio status. Secrets are never sent.

## Song to Chart: the flow

1. **Search** (`GET /api/search?q=Title - Artist`). The chart catalog is searched
   first. Then MusicBrainz, iTunes and Deezer are searched (no keys needed), plus
   Spotify and YouTube when their keys are set. Results show title, artist, album,
   year, duration, ISRC, the providers that know the recording, and its version.
   Versions are studio, live, remaster, demo, acoustic, remix, instrumental or cover,
   read from the title and album. Each recording gets a stable id: from its ISRC, else
   from the provider's track id, else from the title, artist and version. Every
   provider reports its state: searched, unavailable (with the reason) or not
   configured. A failed provider is never shown as an empty result. If nothing is
   found, the song can be added by hand.
2. **Source resolution** (`drum_agent/web/sources.py`). The app checks, in order:
   - `EXISTING_CHART`: a chart is already stored.
   - `AUTHORIZED_ASSET`: the operator put the recording in `DRUM_AGENT_ASSET_DIR`
     with a rights basis in `assets.json`.
   - `USER_UPLOAD`: the user uploaded the recording (`LOCAL_FILE`: the personal app
     took it from the user's music folders, see "A song from its name" below).
   - `MUSIC_FOLDERS`: personal mode only. The app can look for the recording among
     the user's own audio files and chart it.
   - `LICENSED_SOURCE`: a licensed audio provider. None is configured in this build,
     and the app says so.
   - `NEEDS_SOURCE`: the recording is identified, but no authorized audio is
     available. The page offers an upload.

   Streaming services (Spotify, Apple Music, Deezer...) are metadata only: their
   DRM-protected audio and previews are never downloaded, cached or transcribed. Video
   sites too: YouTube is searched through the YouTube Data API (with a key) and a song
   found there plays in YouTube's own embedded player on the song page; its audio is
   never downloaded.
3. **Upload** (`POST /api/songs/{id}/upload`). An upload is a file plus a rights
   basis: own, permission, licensed, public_domain or original, and in personal mode
   also personal (for the user's own practice). The rights gate
   (`drum_agent/rights.py`) runs before anything is decoded.
   `drum_agent/audio/prepare.py` then checks the extension, the size, the file
   signature and the ffprobe stream properties. It decodes the audio to the internal
   format (44.1 kHz, 2 channels, 16-bit WAV) with the timeline untouched. It refuses
   files that are truncated (a decode shorter than the header announces), too short,
   too long or silent, each with a reason the page shows. Each model resamples from
   the internal file to what it needs; the classifier uses 44.1 kHz mono.
   The same file uploaded again is the same source, and gets the same job.
4. **Transcription job** (`drum_agent/web/jobs.py`). The job runs on a worker thread
   and its state is stored in SQLite. Its stages are prepare, detect, beats,
   measures, sections, validate, render, view and save. The transcriber reports the
   first five itself as it reaches them, so the stage shown is the work being done.
   - Jobs are idempotent per recording (the audio's SHA-256) and engine version.
   - Cancellation takes effect at the next stage boundary.
   - A failed or cancelled job can be retried.
   - A job interrupted by a restart is queued again once, then reported as failed.
5. **Validation** (`drum_agent/validate.py`). These checks run on the score itself:
   - every bar holds exactly its time signature (only bar 1 may be a pickup);
   - every stroke lies inside its bar, on the 32nd-note or triplet grid;
   - no duplicate strokes, and every instrument is in the kit;
   - tempo between 20 and 400 BPM, and sections in order;
   - bar start times increase, and each bar lasts what its tempo says;
   - every stroke lies inside the notated timeline, which runs from the recording's
     first stroke to its last;
   - nearly every detected stroke is notated.

   Separately, the PDF (through LilyPond's MIDI), the MusicXML and the MIDI are
   checked against the score (`drum_agent/verify.py`).
6. **Status.** A chart is `COMPLETE` only when every check passes, the exports
   match, and no bar is flagged for review. Otherwise it is `NEEDS_CORRECTION`. A
   song's status is one of `NOT_STARTED`, `ANALYZING`, `TRANSCRIBING`, `VERIFYING`,
   `NEEDS_SOURCE`, `NEEDS_CORRECTION` or `COMPLETE`, derived from its jobs and charts.
   The printed chart still says "Automatic transcription, unverified": `COMPLETE`
   means complete and consistent. It does not mean a person checked every note.
7. **Chart view.** The page shows the engraved pages as SVG, drawn by LilyPond from
   the same `.ly` file as the PDF, with each barline tagged with its bar number. From
   the tags, `drum_agent/web/view.py` builds a box for every engraved bar. The page
   then offers:
   - jumping to a section or a bar number;
   - zoom;
   - stepping through the bars flagged for review;
   - following playback of the source recording, using the bars' performed start
     times from the score;
   - printing (print CSS lays the pages out one per sheet, like the PDF);
   - downloading the PDF, MusicXML or MIDI.
8. **Corrections make versions.** Confirming a flagged bar after listening, or
   renaming sections, creates a new chart version (v2, v3 ...) with its own
   validation and files. Earlier versions are kept.

## Claude

Claude is optional: every feature works without it. When `ANTHROPIC_API_KEY` and
`DRUM_AGENT_ANTHROPIC_MODEL` are set, it helps in three places. Each time it gets a
structured request, and its answer is validated before anything uses it:

- **Reading a beat description.** The answer is generator settings in a JSON schema
  (enums and numbers), clamped by `BeatSpec.from_dict` and merged under the rules'
  exact readings. Claude never writes strokes: the generator does.
- **Edit requests the rules can't read.** Claude rewrites the request as the editor's
  own commands, which the rule-based editor then applies and checks; or it says the
  request is unsupported and why.
- **Section names for a transcription.** Described below.

`POST /api/charts/{id}/suggest-sections` asks Claude to name the chart's sections
(Intro, Verse, Chorus ...). The transcriber only letters them A, B, C.

- **What is sent.** Claude gets a compact factual description of each section: its
  first bar and length, density, main cymbal, crashes, tom strokes, and which sections
  share a pattern. It also gets the title and artist. No audio, file paths or
  configuration are sent.
- **What comes back.** The answer is structured output (a JSON schema). It is then
  validated: one name per existing section, from a fixed vocabulary, at exactly the
  existing boundaries. Claude cannot add or move a boundary, or change a note or a
  tempo.
- **Applying it.** A suggestion changes nothing until the user applies it, which
  makes a new version.
- **Configuration.**
  - `ANTHROPIC_API_KEY` and `DRUM_AGENT_ANTHROPIC_MODEL` (a current model id from
    Anthropic's models overview). Without them the button is disabled and the API
    answers 503 `not_configured`.
  - The base URL is the public API unless `DRUM_AGENT_ANTHROPIC_BASE_URL` is set.
  - The timeout is 45 s with one retry.
- **Errors.** Authentication, permission, unknown model, rate limit, timeout,
  connection, refusal, truncation and an answer that doesn't fit the chart are each
  reported as such.

## A song from its name (the personal app)

Personal mode is one person using the app on their own computer: the Windows app
(`drum_agent/desktop.py`, [DESKTOP.md](DESKTOP.md)) or `serve --personal`, which only
listens on 127.0.0.1. `GET /api/health` says `"mode": "personal"` and whether there is a
music folder to look in (`"library"`: `~/Music` and the folders in `DRUM_AGENT_MUSIC_DIRS`).
Then picking a song is enough, when the user has its recording:

1. The song page asks once to confirm the chart is for the user's own practice ("I won't
   post it publicly"). The choice is remembered in the browser. With it, choosing a
   search result ("Make the chart") starts at once.
2. `POST /api/songs/{id}/library` (`{"personal": true}`) queues a `library` job
   (`drum_agent/web/library.py`):
   - `search`: the music folders, read only (`song/local.py`: tags or file names, at most
     20,000 files and 20 s), ranked by title and artist, the plain recording before a
     live take or a remix. Nothing found fails the job with what to do instead.
   - The best match is decoded like an upload into the song's source (kind `library`,
     rights `personal`); the user's file is only read.
   - Then the transcription stages. The chart opens by itself when it is ready.
3. The song page names the file used and lists the other matches
   (`GET /api/songs/{id}/library`; "Use this" starts a job on that one; a picked file must
   be an audio file inside a music folder). One job per song and file: asking twice
   returns the same job.

A personal chart prints "Transcribed for personal practice. Not for distribution." on
every page and in every file, is shown with a "Personal practice" badge, and is never
marked shareable (`"shareable": false`); a version edited from it keeps its basis. A
shared server (the default, and the live studio) answers 403 to both routes, never reads
its own disk for a song, and refuses the personal basis for uploads. Tests:
`tests/test_web.py`, `tests/e2e/library.e2e.js`.

## Endpoints

See the docstrings of `drum_agent/web/app.py` (songs, jobs, charts) and
`drum_agent/web/studio.py` (kit and samples, beats, previews, drafts, versions,
library). `GET /api/health` reports:

- LilyPond, ffmpeg, ffprobe, the classifier weights and the database;
- each provider's state, and whether Claude is configured (never the key).

It answers 503 when a required dependency is missing.

Files are served only from a fixed list: `chart.pdf`, `chart.musicxml`, `chart.mid`,
`chart.json` and the `page-N.svg` pages. All ids are checked against their format
before any path is built. Uploaded file names are display names only: stored audio
is named by its SHA-256.

## Storage

`DRUM_AGENT_DATA_DIR` (default `~/.drum_agent/web`) holds:

- `drum_agent.sqlite3`, with the tables `songs`, `sources`, `jobs` and `charts`. A
  project is a `songs` row of kind `song` or `beat`, with an optional draft. A job is of
  kind `transcribe` or `generate`. A chart version can carry a note. The columns are in
  `drum_agent/web/store.py`. A database from an earlier version is migrated in place
  when the server starts. Chart versions are immutable.
- `sources/<sha256>.wav`, the normalized audio, served back only to the chart's
  playback.
- `charts/<id>/`, which holds `chart.json` (the score), the PDF, MusicXML, MIDI,
  LilyPond source, reports, `validation.json`, `view.json` and the SVG pages.
- `previews/<hash>/`, the on-screen pages of working copies. Only the newest 150 are
  kept.
- `samples/<instrument>.wav`, the rendered drum sounds.

## Visitors of a shared server

The app has no user accounts. On a shared server every browser is its own visitor with a
private workspace (`drum_agent/web/owners.py`): its first request gets a random owner token
in a cookie (HttpOnly, SameSite=Lax, Secure over HTTPS, a year), and its songs, beats,
uploads, jobs and chart versions belong to it (`songs.owner`). Lists, the search's
catalog and every lookup by id show a visitor only their own projects and the operator's
seeded examples; anything else answers 404, as if it didn't exist. A song's id is the
visitor's own (derived from the catalog id and the token), so two visitors charting the
same song never share a project, its upload or its chart. Examples have no owner: anyone
can open, play and print them, nobody can change them (403); "Duplicate" makes the
visitor's own copy. Clearing the browser's cookies loses the workspace. In personal mode
(one person, their own computer) nothing is scoped and no cookie is set.

The app doesn't redistribute uploaded audio or charts: a recording is played back only in
its own project's chart.

## Transcription engine

The engine is the project's own:

- candidate onsets from the spectrogram;
- a trained onset classifier (`drum_agent/data/onset_classifier.npz`,
  [MODELS.md](MODELS.md));
- beat, meter and downbeat tracking;
- exact quantization into bars.

Its measured accuracy is in [LIMITATIONS.md](LIMITATIONS.md).

When PyTorch and demucs are installed (the Windows app has them), a band recording's
drums are first separated from the other instruments with HTDemucs; the job shows it as
its own stage ("Separating the drums from the band") and the chart's notes say so. It was
measured on real recordings and synthesized charts before it was turned on: see
[MODELS.md](MODELS.md). Omnizart (an alternative drum transcription model) was
considered but not evaluated.
